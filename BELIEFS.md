# BELIEFS.md

The constitution of this system. Every file in this project must be consistent
with it. When a design decision has two valid answers, this file decides, and
the decision must state which belief decided it.

---

## 1. Intelligence over workflows

Workflows, systems and processes are not the driver. The intelligence behind
them is.

The purpose of automating any workflow is to free time for the intelligence
layer. Never to replace it.

**In this OS:** automation earns its place by returning attention to thinking.
A feature that runs on its own but produces nothing a mind acts on is dead
weight, however impressive it is.

---

## 2. Intelligence and process are non-substitutable

Intelligence builds processes. Processes sharpen intelligence. It is a feedback
loop, not a hierarchy. Neither one is the senior partner, and neither can stand
in for the other.

**In this OS:** every process must have a return path into the intelligence
layer. A process that only consumes judgment and never feeds it back is broken
by design, not merely incomplete.

---

## 3. Human and model are two hemispheres of one brain

They work in synergy. Neither replaces the other.

The human supplies judgment and context. The model supplies technical depth the
human does not have.

**In this OS:** the model never silently decides on the human's behalf, and the
human is never made to do work the model can carry. Interfaces are built for a
brain operating in two halves. The model shows its reasoning so judgment can
engage with it, not just with its conclusion.

---

## 4. Intelligence is knowledge RETURNING, not knowledge generated

Intelligence is constituted by knowledge arriving back at a common location.
Generation without arrival changes nothing structurally.

A brilliant answer that lands nowhere leaves the system exactly as it was.

**In this OS:** every memory, logging and knowledge feature is designed around
arrival. Answers, learnings and outcomes flow back to one common substrate.
Output is not the deliverable. The deliverable is what the substrate holds
afterwards. Any feature that generates without a return path is incomplete, no
matter how good its output.

---

## 5. The transfer problem is the core gap

A system that goes superhuman in one domain and relearns the adjacent one from
scratch has not carried over the abstraction. It has memorised, not understood.

**In this OS:** build to carry abstractions across contexts, never to silo them.
Knowledge stored under one topic must be reachable from a different one when the
underlying structure is the same. Storage that is organised only by where
something came from is a silo with a filename.

---

## 6. Routing is the crux, not retrieval

When a problem arrives, the system must shift between its different threads of
understanding and route to the right one.

Retrieval is a solved problem. Routing is not.

**In this OS:** design for routing. The hard question is never "can we find
matching text", it is "which mode of understanding does this problem belong
to, and did we enter it." Effort spent on recognising the kind of problem beats
effort spent on finding more matches for it.

---

## 7. Prefer underspecified real-world goals

"Bake a cake" forces a system to figure things out. A rigid specification lets
it comply without understanding.

**In this OS:** state the outcome, leave the path open. Tasks and prompts are
written to require figuring out, not to be satisfied by following. A prompt that
can be completed without understanding the goal is a prompt that taught the
system nothing.

---

## How to use this file

- Every file states, in one line, which belief it serves.
- A file that serves no belief should not exist. Question it before writing it.
- No workflow, automation or process file is added for its own sake. Each one
  exists to protect or amplify the intelligence layer, and says how.
- Design decisions are resolved here, and the resolution names the belief.
